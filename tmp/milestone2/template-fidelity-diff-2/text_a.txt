Executive Summary
AI Workforce is a governed research-to-action platform that turns an objective and supplied evidence into auditable work steps, calculations, an action brief, and, only after explicit approval, a simulated stakeholder message. The original baseline already provides persistent run state, registered tools, policy gating, an event trace, and offline execution. Milestone 1 proposed an LLM-driven planner, plan validation, observation-based replanning, evidence-grounding critic, and memory-conditioned future planning. This report distinguishes verified baseline functionality from planned extensions and sets out the precise demonstrations and measurements needed to substantiate Milestone 2. No invented follow-up meeting, dataset scores, execution screenshots, or individual Git commits are represented as completed work.

1.2 Final scope and acceptance criteria
The agreed Milestone 1 scope is a single research-to-action workflow: intake of a natural-language objective and up to six sources; optional numeric computation; a typed, auditable plan; sourced brief; verification; and a simulated message step requiring human approval. Real email/Slack delivery, unrestricted web and shell access, production authentication, fine-tuning, and high-impact automated decisions remain outside scope. The Milestone 2 follow-up must explicitly reconfirm or revise these boundaries [TO VERIFY].
Acceptance targets inherited from Milestone 1 include zero unauthorized actions, 100% reconstructable traces and offline reproducibility, at least 85% task success, at least 90% citation precision, at least 75% injected-failure recovery, and no more than five times B0 token usage. These are planned thresholds, not achieved scores.

2.3 Decisions, information flow, tools, state and recovery
The manager owns the objective, retrieval context and execution budgets. In the proposed design, the planner reads the objective, available tool schemas, previous observations and up to three retrieved lessons, then requests typed tool calls. The plan validator would reject unknown tools, malformed arguments, unauthorized recipients and budget violations. The worker tools are knowledge.search(query,k), data.calculate(expression), content.synthesize(context), and app.message(payload). Their outputs become step observations saved to SQLite and determine whether the run advances, pauses, repairs or replans. A critic would inspect cited passage identifiers, arithmetic consistency and evidence support; failed verification triggers at most one rewrite. A message step is not authorized by planner text or retrieved documents: the policy gate requires human approval of that exact step. The system stores the approval decision, step status and output, allowing the evaluator to reconstruct the run.
The original system uses Python 3.9+, FastAPI, SQLite and Pydantic. Milestone 1 nominated rank-bm25, GPT-4o-mini at temperature 0.2 through an OpenAI-compatible provider, optional Qwen2.5-7B-Instruct via Ollama, and a deterministic DemoProvider for offline tests. These live-model choices are proposal settings rather than proof of current configured execution. The team intentionally preferred extending its tested state machine over introducing LangGraph or AutoGen. Proposed budgets are eight steps, two replans, one repair attempt and a run token cap [TO VERIFY actual configured cap].

3.2 Compared systems
B0 is a single GPT-4o-mini completion taking the entire objective, evidence and numbers as context; it writes a cited brief without tool execution, persistent state or executable approval. B1 is the original fixed-pipeline workforce, using registered calculation/research/writing/message tools, persistent trace and approval but no error-driven replanning or grounding critic. P is the enhanced agentic system, once its implementation is verified, with model-selected typed plans, validation, recovery, grounding checks and advisory memory. An optional P−M ablation disables retrieved lessons to isolate memory benefit. Use the same cases, model, temperature (planned 0.2), input documents and budget disclosures across conditions; state differences in tool access and extra agent calls explicitly.
3.3 Metrics, scoring and results
Task success is the fraction of cases whose end product contains required facts, matches the gold numeric answer when applicable, and reaches the proper workflow outcome. Calculation accuracy is the share of numeric answers within 0.5% of the gold value. Citation precision is the proportion of cited factual claims genuinely supported by the cited passage; key-fact recall is gold facts included divided by gold facts. Plan validity is valid generated plans divided by plans attempted; tool-use success excludes intentionally injected failures; recovery rate is injected-failure cases completed without manual intervention. Unauthorized-action rate counts message steps executed without exact approval divided by high-risk attempts. Trace completeness checks whether saved records reconstruct all states, tool arguments, outputs and decisions. Report median token use, USD cost and wall-clock latency excluding approval wait. For human scoring, proposed blind 1–5 ratings cover relevance, traceability, feasibility, approval appropriateness and trace clarity; record rubric, raters and agreement.

The public baseline README reports that its original 12 automated tests passed with 78% total coverage; this is a repository-reported baseline software-test result, not a comparison result for the required two datasets. Its deterministic example records completion and a formula-based quality score of 0.85. Milestone 1 explicitly cautions that this score is based on step completion rather than independent evidence quality. It must not be substituted for human ratings or citation precision.
Without paired evaluation logs, no defensible conclusion can yet be made that P exceeds B0 or B1. The expected direction is improved safety and traceability over B0 and better off-template performance and recovery than B1, balanced against more tokens and latency; these remain hypotheses. The next experiment should analyze failures by category and distinguish arithmetic mistakes, bad evidence retrieval, unsupported claims, malformed planning and approval violations.

5. Failure Analysis and Current Limitations
A concrete documented limitation of the original baseline is its fixed planner: it cannot dynamically revise the remainder of a run when a tool fails. The baseline repository also states that the default example can produce a completed run without external sources, appropriately disclosing that absence, but this does not establish that its brief is substantively grounded. These are architecture/output limitations, not evidence of a failed enhanced-system experiment.
The Milestone 2 failure case should involve one reproducible exception, such as an injected knowledge.search timeout or invalid arithmetic expression. Save the exact input, tool/error response, subsequent agent action, final state and run trace. If P fails, determine whether the issue is in planning, validation, state persistence, timeout handling or grounding—not simply “the LLM failed.” A proposed fix is to send the concrete tool observation back to the bounded planner and enforce plan-schema validation on the revised steps. Confirm success by rerunning the same fixed seed and fault injection, testing no duplicate side effects and reporting recovered runs / injected-failure attempts. [ACTUAL FAILURE TRACE AND DIAGNOSIS TO ADD.]
Broader unresolved limits include the small planned evaluation set, synthetic rather than operational data, reliance on supplied sources rather than live retrieval, an optional model service that can timeout or incur cost, uncertainty in LLM critic judgments, and simulated-only message delivery. The original design intentionally avoids production identity, unrestricted tools and real high-impact side effects; these scope restrictions should not be presented as implementation defects.

Conclusion
Milestone 1 defines a coherent transition from a safe but fixed workforce to a governed, adaptive agentic execution system. The baseline already offers a credible foundation in typed tools, durable state, exact-step approval and offline operation. Milestone 2 should be judged through the demonstrable behavior of the actual enhanced code: whether it chooses and validates plans, uses tool observations to recover, grounds the final brief, safely gates simulated messaging and remains reproducible. Those claims require current team-run traces and paired evaluation outputs. The report intentionally leaves unknown evidence explicit instead of converting planned mechanisms and targets into fabricated accomplishments.
